# Release and integration

## Discover the real contract

Before touching pixels, read the store's current lineup and its hero renderer/editor if present. Record a small project brief with:

- The named time zone, configured release cadence and exact saved ISO instant; use the lineup's timestamp across daylight-saving changes.
- Product IDs, garment/style identifiers, pictured variant/color, hidden or published state, and dated provider/editor reference URLs.
- Exact print revision/upload identity, original file dimensions/transparency and SHA-256. Match the revision used by the product, which can differ from the newest library favorite.
- Desktop/mobile source dimensions, minimum native resolution, encoding/size limits, viewport crop behavior, safe region and clickable-region schema.
- Required copy, verified offers, brand art direction, permitted people/props and requested number of directions.
- Available editor, saved preview, approval/scheduling controls and current saved version/status.

Keep this brand data in the project or private working package, never the installed skill. Do not copy another store's price, date, product IDs, model roster or access tokens.

Hidden scheduled products can be inspected through authorized private previews. Do not publish them merely to obtain a reference. If the lineup is incomplete or the product's print revision is unverified, continue layout planning but label the affected garment/release unresolved. Do not substitute a different design or invent exact measurements.

## Save through a supported integration

Where an editor exists, upload the approved desktop and mobile files, choose the actual products and pictured colors, and assign every garment's click rectangle in each view. An image upload is not a saved hero. Save a private draft and inspect its **saved** preview. Reopen the editor to confirm the exact pair, destinations, rectangles, copy and version persisted.

Do not overwrite a stale version. Reload and reconcile concurrent changes. If saving as a draft would withdraw an existing schedule, use it only when that withdrawal is intended. An authorized replacement can use the application's schedule/publish action directly, followed by saved-preview checks; do not request the same approval twice.

Configure the selected release only under the owner's existing authorization. Recheck product membership, visibility and pictured colors before approval. A future approved hero is scheduled, not live. When live verification is in scope, use a fresh public page after the actual activation instant and confirm the current files, links and fallback/expiry behavior.

Normal content changes should use the target's supported workflow, not direct database writes, Blob overwrites, weekly code mappings or unrelated product publication. If there is no integration, deliver the selected package and report scheduling unavailable; implementing a scheduler is a separate code change.

## Browser verification

Use a fresh phone load around 390 CSS px, a typical desktop, a wide desktop, and both sides of the actual breakpoint. Inspect source selection and network requests as well as screenshots; resizing an already loaded page may retain a larger image candidate. Both compositions need their own readable hierarchy, not the same poster reduced until the type disappears.

Click every garment and its visible shop label in each view. Confirm product and pictured color. Test keyboard access and visible focus, descriptive image text, native equivalent title/offer and destination labels. Preserve existing accessible weekly content and structured data when integrating a poster; an image alone cannot replace them. Report private-preview success separately from public access, optimized-image caching, scheduling and live activation.
