# Retain a selected package, not the entire experiment

Use the host's existing private asset storage for operational artwork and final image files, with revision and upload evidence in its database. In this template that means private Blob storage and database records; local work belongs in ignored staging. Keep working concepts, rejected generations and duplicate QA renders there or in an agreed private archive. Do not delete working sources until the chosen pair and required archive are independently restored and checked. A hosted gallery alone is not a source backup.

A small durable private package should contain, or locate through verified private asset references:

- Final desktop/mobile lossless masters and exact upload files.
- The approved source artwork or its stable authoritative location, with revision identity, dimensions and hash.
- Final scenery/lettering layers, garment cutouts and only the accepted patches needed to reproduce or edit the pair.
- Dated actual garment/color references, calibrated bounds and cutout origin, model identity references only when applicable and authorized.
- A composition record with relative input paths, source hashes, decoded dimensions, transforms, ordering, export settings and final hashes.
- Complete relevant prompts and accepted refinements; keep tool/model versions when the host exposes them. Do not invent deterministic seeds or promise identity recovery from a prompt alone.
- A historical release receipt: selected direction, exact activation instant and time zone, products/colors, link rectangles for every view, title/offer/description, saved asset IDs and dated verification.

Git is not the default image archive, even in a private repository. Keep operational print artwork, final hero masters/uploads, garment cutouts and model references out of Git unless the receiving project's policy and owner explicitly authorize those particular assets there. This template's policy keeps them in private storage. Reusable skills and template examples must not accumulate a receiving store's operational data.

Compact reusable instructions, redacted prompts, geometry recipes and restoration procedures may go in Git when the host's policy permits. Keep sensitive product/model metadata, private asset locators, credentials and signed URLs out; retain private receipts with the assets. Record stable asset/revision identities and hashes there, then obtain fresh authorized access when restoring. Do not introduce a service or make images public implicitly. Verify checksums after restoring into a fresh directory, with the working concept folder unavailable. Do not keep absolute local paths as the only source of truth.

Where a deterministic compositor is used, replay it with pinned library versions. Compare decoded master pixels and exact upload bytes with the selected final files. A hash match proves retained file identity; reproducing a render proves the recipe's output; neither proves that placement was correct. Preserve the independent visual review too.

If a source recipe uses an intermediate image conversion, test before removing it: a seemingly redundant PNG round-trip can change alpha/compositing pixels. Extend a shared renderer for a needed operation rather than creating a new per-design pipeline.

An archive receipt is not a live status API. Re-read the store before another release. Retaining a final package does not approve, schedule or publish it.
