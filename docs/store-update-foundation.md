# Update foundation for standalone stores

Standalone copies are the supported model. Any participating store can contribute a sanitized reusable fix to the canonical template and receive reviewed releases back. Optional features ship as code with activation disabled. Each store retains its own brand, data, provider accounts, credentials and deployment authority. The shirts travel; the secrets stay home.

## Implementation gates

1. **Reconcile and triage.** Catch up the source-port ledger, including the actual #24 merge commit. Review template security fixes for the operating source store. Keep a private opt-in store update register outside this repository; seed the operating store and planned rehearsal. Track code gaps separately from verified deployment. Prioritize security ports without waiting for practice-release material.
2. **Compatibility before generation.** Separate owner values from validation/loader code; preserve prior configuration and default omitted activation flags off. Payment identity and retained-data disclosures require explicit receiving-store decisions. Protect merged migration filenames and bytes, and let canonical doc/skill references resolve through checksummed forward-port mappings. Merge this structural change before generating any store.
3. **Release preparation.** Prepare a lightweight record of commit/tree, migration checksums, lockfile digest, included PRs, dependencies, activation and migration/deploy order. Reserve the `template-v` tag namespace before any immutable release. Publication, immutable-release settings and a new test repository require approval; preparation grants none of these.
4. **4a: one store, one real update.** After approval, generate the rehearsal while `main` exactly equals R1. Customize it, then manually apply a real R2 change and an intentional conflict. This proves code integration only: without provider projects it proves neither migration/deploy ordering nor activation. The first real deployment receipt comes from an authorized operating-store port.
5. **4b: permanent upgrade evidence.** Build populated-database upgrade/failure coverage as CI; the existing schema-reset helper proves only fresh installs. Use synthetic local brands for identity/configuration isolation, partial adoption, conflicts, custom migration ordering and disabled features. New cloud resources need separate approval.
6. **Runbook, then automation.** Turn the proven runbook into a store-update skill. Only then automate inspect/prepare/draft PR creation using individual change patches and their full dependency groups. Reconstruct comparison state after partial adoption; never replace a file with a later whole-template snapshot containing skipped work.

## Policies that every update preserves

- **Origin between releases:** record the exact generated root commit/tree and matching template commit/tree. `originRelease` is null unless it exactly matches a release. An earlier release is a comparison anchor, never an invented integrated baseline. GitHub's template generator copies current `main`, not a selected tag.
- **Migration ordering:** never edit, delete or renumber an already merged/applied migration. Keep an incoming canonical name only if it safely follows the receiving store's migration history. Otherwise write a reviewed receiving-store forward migration with a later timestamp, record canonical/local SHA-256 and rationale, and resolve canonical references through that mapping. Do not routinely force out-of-order pushes with `--include-all`.
- **Partial adoption:** record accepted, deferred, skipped and reverted groups with dependencies. Review workflows, scripts, skills and docs as part of their behavior group, including permission changes. A revert receives its own integration/deployment receipt.
- **Activation:** preserve payment identity through rebranding and use the operating store's established identity when porting checkout. Retained subscriber and delivery disclosures reflect data actually held even while features are disabled; do not default an existing store's disclosures away.
- **Merge versus deployment:** require the receiving store's full CI on its exact final head. If GitHub cannot enforce it, confirm it manually before any authorized merge. Verify actual auto-deploy settings and apply required migrations in the reviewed order before merging deploy-triggering code. Record the resulting deployed revision separately.
- **Contributions:** private stores do not need to expose their history to receive an update. Attribution and extraction evidence stay intact. Resolve copyright holder and contribution rights before external code contributions or public visibility; this implementation changes neither license nor visibility.

The private register is operational evidence, not a catalog of every generated copy and not printer stock. No phone-home registration is added. Unknown whole-store origins refuse automated updates but allow individually inspected scoped fixes under [the update contract](store-update-contract.md).
