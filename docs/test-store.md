# Testing a rebranded store

Owner edits belong in `src/lib/store-config.ts`. Ordinary tests use **Fixture Store** from `test/store-config.ts`; changing a merchant name, support address, timezone, weekly schedule or setup status does not require rewriting test expectations. This fixture is a complete object parsed by the same `storeConfigSchema` as the merchant configuration. `test/configured-store-config.ts` supplies the configured version with explicit policies and shipping prices.

Vitest and Storybook select the fixture through `test/store-config-plugin.ts`, resolving both relative and `@/` imports. Production builds have no fixture switch and never import test support. Tests that need configured commerce import `test/configured-store.ts`; tests of an individual gate explicitly turn that gate off. Schema tests exercise invalid owner values, and `scripts/template/store-config.test.mjs` runs under Node without the resolver to validate the actual merchant module. Cadence tests use two validated brands with different timezones and schedules.

`pnpm test:e2e:prepare` builds two disposable source copies: `.tmp/unconfigured-storefront-e2e` for setup/privacy gates and `.tmp/storefront-e2e` for catalog, checkout and publishing journeys. Both receive fixed validated fixture data; neither inherits merchant copy or edits the working source. The TypeScript-aware generator replaces only the exported value initializer, preserving type annotations and associated exports. Fixture builds use the same default Next.js bundler as production. `pnpm test:admin:build` builds the configured admin copy with the local Supabase origin. Browser tests still require the documented disposable databases and local provider fixtures. `pnpm build` separately builds the actual merchant configuration.

The fixture deliberately differs from merchant defaults: it has its own copy, brand name and email, and uses America/Chicago with a Friday 17:30 weekly schedule. This makes accidental fallback to the merchant's UTC Monday schedule visible even before a store is personalized. Browser specs import `test/store-config` explicitly; the architecture lint rule rejects direct merchant configuration imports under `e2e/`, including aliases, relative paths and dynamic imports. Browser storage keys such as `your-store-cart-v1` are the existing runtime serialization protocol, not the merchant's editable name; keep their expectations consistent with production until a separately tested storage migration changes that protocol.

After adding a required configuration field, update both merchant defaults and the complete test fixture. Preserve schema validation and explicit configured/unconfigured coverage. A test fixture should fit the schema like a well-sized shirt, without stretching the safety seams.

For parallel local work, set `PLAYWRIGHT_PORT` and `PLAYWRIGHT_FIXTURE_PORT` for the public suites and `PUBLISHING_E2E_PORT` / `PUBLISHING_E2E_PROVIDER_PORT` for publishing. Keep each run on its own disposable Postgres container or server; the database-name guards remain in force.

CI fails before running unit or baseline database tests if a required test database URL is missing. Local runs print the names of unavailable database suites; those skips are not database verification. The environment list is checked against the actual suites so a newly added database test cannot silently miss the prerequisite check.
