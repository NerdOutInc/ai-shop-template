# Optional storefront features

Choose supported features in `storeConfig.features`; all three start `false` for a new store. Rebuild after changing configuration. These switches are independent, so a store can collect drop-signup requests without running a weekly collection. No manual feature deletion required; the scissors can stay in the sewing kit.

| Field             | When enabled                                                                             | When disabled                                                                                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `about`           | About page, metadata, header/footer links and sitemap entry                              | `/about` returns 404 and those links/metadata are absent                                                                                                         |
| `designOfTheWeek` | Home section, footer jump link, weekly products lead Featured order and admin scheduling | Weekly readers skip database work; scheduling API returns 404; weekly UI is absent                                                                               |
| `dropSignup`      | Signup form and endpoint, once the brand and reviewed policies are ready                 | New signup collection stops at the route and service; retain the Privacy removal contact by setting `privacy.retainedDropSubscribers: true` for an existing list |

`weeklyFeature` is the cadence for the optional weekly collection; changing the switch does not rewrite its schedule. Existing product schedules also control timed storefront visibility. Disable or cancel those schedules in Products before turning off the weekly feature if those releases should stop. The feature switch does not silently cancel saved product visibility decisions or delete stored rows.

Signup requires the default-off confirmation sender, a production deployment, reviewed policies, the database, Resend credentials and an authenticated 15-minute confirmation worker. Enable `SIGNUP_CONFIRMATIONS_ENABLED` only after [confirmation launch checks](drop-signup.md#inbox-confirmation-and-release); the public form is hidden while its sender is unavailable. Preview/local builds do not offer signups. The store-wide queue ceiling defaults to 20 requests per rolling hour; `SIGNUP_CONFIRMATIONS_HOURLY_LIMIT` accepts 1–1000. Worker errors and privacy-safe logs report saturation. This is independent of the optional [weekly drop email](drop-emails.md), also off by default, which requires `privacy.retainedDropEmailRecords: true` and has an unsubscribe link in every message. Verify the support mailbox and the owner’s removal workflow before opening signup. Preserve historical consent during updates; do not reclassify old subscribers as confirmed. For a new store that has never collected subscribers, keep `privacy.retainedDropSubscribers: false` (the default); with signup off, Privacy makes no signup-data or existing-list claims. Before closing a list that has collected subscribers, set `privacy.retainedDropSubscribers: true` and keep it true while subscriber or suppression records are retained. Privacy then keeps the removal contact and collection disclosures without claiming re-signup is available. This flag is public disclosure configuration: it neither deletes records nor suppresses a separate external mailing list. Follow the removal procedure before any external send.

Feature selection does not override setup gates, provider readiness, or visitor marketing choices. Shipping and policy publishing remain independent of these optional features; see [shipping and policy content](storefront-policies.md).
