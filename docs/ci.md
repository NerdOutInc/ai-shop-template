# Continuous integration

`Check` runs on every pull request, including drafts, on pushes to `main`, and for merge queues. It has no changed-path filter. A manual run of `Check` uses the same jobs. Browser checks should not need a calendar invitation.

| Check                                          | Coverage                                                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Foundation checks                              | Structure, migration references, lint, types, formatting, unit and isolated Postgres tests, architecture, skills, artwork, template checks, and the merchant application build |
| Integration checks / Storybook checks          | Chromium component interactions and accessibility checks, followed by the static Storybook build                                                                               |
| Integration checks / Storefront browser checks | Public Chromium, mobile Chromium, and WebKit journeys; configured catalog and publishing HTTP/browser journeys against disposable local Postgres                               |
| Integration checks / Admin browser checks      | Private library, owner setup, Supabase email sign-in, and virtual passkeys against disposable local Supabase Auth                                                              |
| Required checks                                | Fails unless Foundation and all integration jobs succeeded; failure, cancellation, and skipped dependencies cannot count as success                                            |

The `Integration checks` workflow is reusable and can also be dispatched manually for diagnosis. The PR workflow calls the copy at the same commit being checked. It does not rerun the foundation suite. Each integration job has its own runner and required tools; the admin job starts and stops only its local Supabase instance. Publishing runs after a successful fixture build even if a public browser assertion fails, so both suites can report useful failures.

## Required merge gate

In the repository's branch protection or ruleset, require the **Required checks** status from GitHub Actions for `main`. A workflow file schedules checks; it cannot enforce repository settings by itself. A repository generated from this template must configure that rule separately. Confirm that the rule applies to the intended branches and the latest PR head before merging. Do not replace this aggregate with the foundation job alone.

The aggregate uses `always()` so failed or skipped dependencies still produce a result. It accepts only `success` for both the foundation job and the reusable integration workflow. The separate suite names show where to investigate. The `merge_group` event supplies the same gate if the repository later uses a merge queue.

## Isolation and diagnostics

PR jobs use `pull_request`, read-only repository permissions, and checkout with persisted Git credentials disabled. They receive no repository secrets, deployment environment, or inherited secrets. Do not change this to `pull_request_target` to run PR code or add production commerce credentials to make an integration test pass. Fork PRs may need GitHub's normal workflow approval before jobs run.

Database URLs name disposable databases created inside each hosted job. Provider requests use the existing offline fixtures and synthetic credentials. Admin Auth keys are generated by the local Supabase instance and remain in its ignored status file; that file is not an artifact. Passing these checks verifies the test environments, not a live shop's credentials, deployment, payment capture, or fulfillment.

Node uses the repository's supported major version, pnpm uses `packageManager`, and every job installs with the frozen lockfile. The pnpm store and Python package downloads are cached. Browser binaries are installed from the locked Playwright dependency; browser downloads and application builds are not shared between jobs, preventing stale fixture configuration from crossing suites.

On failure, open the failing step and its suite-specific artifact: `storybook-diagnostics`, `storefront-browser-diagnostics`, `publishing-browser-diagnostics`, or `admin-browser-diagnostics`. Browser artifacts include the HTML report, retained traces, and failure screenshots. Storybook uploads screenshots and logs when available. Artifacts expire after seven days; a failure before a browser starts may have logs only. Supabase cleanup runs after both success and failure.

For local validation, use `pnpm check` for the foundation and `pnpm check:all` for the full suite with its local database, Supabase, and browser prerequisites. Never substitute a skipped database test for a passing integration check. See [the architecture guide](architecture.md#enforcement-and-verification) and [store setup](store-setup.md#verify-before-accepting-real-orders).
