# Store operating requirements and budget

Planning snapshot checked against the linked provider documentation on **2026-09-28 UTC**. Recheck prices, quotas and account eligibility before committing to a plan. These estimates do not create subscriptions or authorize spending. The bills do not care how charming the shirts are.

## Hosting and account boundaries

A commercial store on Vercel with this template's supplied schedules needs **Pro or Enterprise**. [Hobby is for non-commercial personal use](https://vercel.com/docs/plans/hobby), and its [daily-only cron limit](https://vercel.com/docs/cron-jobs/usage-and-pricing) cannot run the publishing and stock schedules. More frequent expressions fail deployment. Reducing stock refresh to once daily would violate this app's two-hour freshness cutoff. Another host needs equivalent authenticated recurring jobs and a separately reviewed deployment plan.

[Supabase Free](https://supabase.com/pricing) currently permits two active projects and can pause after a week of inactivity. A second project alone does not force Pro. For an operating store, choose availability and backup requirements deliberately; do not treat a spare free project as production-readiness evidence. Shared organization billing also means shared usage allowances and administrative access: separate projects are not separate billing organizations. See [Supabase billing](https://supabase.com/docs/guides/platform/billing-on-supabase).

Printify shop separation alone does not contain a compromised account-wide token or another shop's traffic. Use separate accounts for the stronger boundary. An explicitly accepted shared-account exception must name the shared credential reach, request budget, billing and incident owner. Separate tokens with narrower operation scopes help least privilege, but do not create shop isolation. Do not move existing accounts or recreate products as part of setup documentation changes.

## Illustrative monthly base

Assume one Vercel Pro team with one deploying seat, one Supabase Pro organization, and one continuously running Micro production database per store. For `N >= 1` stores, the approximate subscription/compute base is:

```text
$20 Vercel + $25 Supabase + max($0, $10 × N − $10 compute credit)
= approximately $45 + $10 × (N − 1) per month
```

That is about **$45 for one production store**, **$55 total for two**, or **$65 total for three** under these assumptions. A separate paid Micro preview database adds about $10/month while running continuously. The example excludes taxes, usage above included credits, extra seats/organizations, larger compute, storage/transfer overages, optional backups/add-ons, domains, email plans, CI overages, payment fees and manufacturing/shipping. Existing projects may already consume the organization's credit. Actual hourly compute and project choices change the bill. A shared engine reduces repeated code work, not these per-store operational obligations.

## Required and optional recurring work

The schedules below come from [`scripts/vercel-crons.example.json`](../scripts/vercel-crons.example.json). They are inactive until configured for the intended production deployment; a schedule in a repository does not prove it ran.

| Job                                     | Example schedule | Operational requirement                                                                                                                                                                                                 |
| --------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/internal/printify-publishing`     | Every minute     | Required for reliable publication/retry processing when publishing is enabled; a webhook's best-effort callback is insufficient                                                                                         |
| `/api/internal/catalog-sync/stock`      | Every 30 minutes | Required for a saleable catalog; stock observations at least two hours old close browsing availability and cause feeds to return 503                                                                                    |
| `/api/internal/catalog-sync/popularity` | Every six hours  | Required while the storefront exposes Most Popular, as it does today; observations expire after 24 hours. Treat as optional only after implementing a supported way to disable that feature and its health expectations |
| `/api/internal/order-alerts`            | Hourly           | Optional; enable only with verified owner-email delivery and `ORDER_ALERTS_ENABLED`                                                                                                                                     |
| GitHub publishing monitor               | Twice hourly     | Optional but recommended incident detection; disabling it does not disable the required workers                                                                                                                         |

In a 30-day month, the [half-hour monitor](../.github/workflows/publishing-monitor.yml) has **1,440 scheduled opportunities**, each with one standard `ubuntu-latest` job and a five-minute timeout. GitHub [rounds each started job up to a whole minute](https://docs.github.com/en/billing/reference/actions-runner-pricing). Budget about **1,440 runner minutes per store per month** when each scheduled job runs for at most one minute, or **7,200 minutes** when each runs for five minutes. Missed schedules, interruptions, manual runs and reruns change the total; these are planning scenarios, not measured usage or a billing cap.

In [private or internal repositories](https://docs.github.com/en/enterprise-cloud%40latest/actions/reference/runners/github-hosted-runners), these minutes consume the repository owner's included allowance before overage billing. The allowance is shared with other repositories and CI: [GitHub Free includes 2,000 minutes/month](https://docs.github.com/en/billing/concepts/product-billing/github-actions), Pro and Team include 3,000, and Enterprise Cloud includes 50,000. Two monitors at 1,440 minutes each exceed a Free allowance before other CI. Standard runners are free for public repositories. The monitor job is skipped before a runner starts unless `PUBLISHING_MONITOR_ENABLED` is `true` and the run targets the default branch.

The minute publishing schedule has 43,200 scheduled opportunities per store; an idle worker makes no Printify call, but hosting invocation costs still deserve measurement. Budget provider reads across stock scans, checkout, order recovery and optional jobs; separate tokens do not multiply a shared account's quota.

Before launch, verify authenticated successful recurring runs on the intended project, durable stock freshness and retry recovery. A manual initialization or an HTTP 200 from a disabled/skipped job is insufficient. Previews need isolated resources and direct test invocations because Vercel schedules run on production deployments. Follow [catalog refresh](catalog-background-refresh.md), [publishing](printify-publishing.md) and [owner alerts](order-shipping-alerts.md), and record those receipts separately from `setup:check` configuration results.
