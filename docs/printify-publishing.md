# Publish from Printify to your store

Printify's **Publish** button starts a request to this storefront. The website records the request, updates its published product snapshot, and reports the result to Printify so the product can be edited again. The shirts can hang around; the publishing lock should not.

This workflow uses the existing private Postgres database. A product's saved Printify draft and its published storefront snapshot are different records. Saving an edit in Printify is not a request to show that edit to customers. Publication applies the fields selected in Printify; a failed update preserves the previous published version.

For library-managed products, [approved artwork publication](artwork-previews.md#automatic-approved-artwork-publication) adds a bounded transparent public derivative to the same saved snapshot after an exact immutable revision/production-fingerprint match. Private originals and full print files stay private. The [design-library guide](admin-design-library.md) covers creating/reusing drafts and reconciling existing bindings before release; these are separate from payment fulfillment.

## Application endpoints

| Endpoint                                      | Purpose                                             | Authentication                        |
| --------------------------------------------- | --------------------------------------------------- | ------------------------------------- |
| `POST /api/webhooks/printify`                 | Validate and durably queue a publishing event       | Shop-specific Printify HMAC signature |
| `GET /api/internal/printify-publishing`       | Process up to five eligible jobs                    | `Authorization: Bearer <CRON_SECRET>` |
| `POST /api/internal/printify-publishing`      | Run the same bounded processing manually            | Same bearer credential                |
| `POST /api/internal/product-images/backfill`  | Copy images from a bounded published snapshot batch | Same bearer credential                |
| `POST /api/internal/product-artwork/backfill` | Repair missing artwork on saved publications        | Same bearer credential                |

All these endpoints use the Node.js runtime and a 60-second maximum duration. The webhook returns 503 when `PRINTIFY_PUBLISHING_ENABLED` is false. The worker authenticates first, then returns HTTP 200 with `{ "processed": false, "reason": "disabled" }` while the feature is off, without accessing the database or Printify. Missing required route credentials still fail closed; configure `CRON_SECRET` before deploying the schedule even when publishing will remain disabled.

The webhook accepts JSON bodies up to 64 KiB. It verifies the signature against the exact UTF-8 body before parsing the event. It returns HTTP 200 only after the event has been saved. Database failure returns 500; malformed or unauthenticated requests return 400. Responses and logs exclude credentials, raw payloads, database errors, and provider response bodies.

After saving an event, the route requests one prompt processing attempt through Next.js `after()`. A recurring authenticated worker trigger is still required: the prompt attempt can be interrupted after acknowledgment. Never treat an in-memory callback or a successful HTTP 200 delivery as proof that publication completed.

## Configure an environment

The template ships no active cron schedule. Use the [supported Pro/Enterprise hosting and worker cadence](store-setup.md#supported-hosting-and-scheduled-workers); Hobby's daily-only cron cannot provide this recovery/stock refresh schedule and Hobby is noncommercial. After reviewing authorized costs, merge the required schedules from `scripts/vercel-crons.example.json` into `vercel.json`; a production deployment then registers them. Application changes alone do not register a webhook, migrate a remote database, or publish existing products. Configure and test these together in the intended environment before enabling the integration there.

1. Apply [the fresh database baseline](../supabase/migrations/20260928000354_storefront_baseline.sql) to an empty, dedicated application database through [Supabase CLI `db push` and verify migration history](store-setup.md#database-and-tls). Use the session-pooler or direct runtime connection described there, because the worker uses session advisory locks. The `commerce` tables remain private to the server.
2. Use the [provisioned and verified restricted runtime login](store-setup.md#provision-the-runtime-login), not the migration-owner credential. Set `DATABASE_URL`, `DATABASE_SSL_CA` with the Supabase CA's complete PEM certificate, `PRINTIFY_SHOP_ID`, `PRINTIFY_PUBLISHING_API_TOKEN`, and the canonical `NEXT_PUBLIC_SITE_URL`. Keep `sslmode=verify-full` in the database URL; see [database TLS setup](store-setup.md) for certificate configuration. The dedicated publishing token needs only `products.read` and `products.write`. Keep `PRINTIFY_API_TOKEN` and its existing catalog/checkout scopes separate; an older read-only catalog token cannot acknowledge publication.
3. Generate a separate random `PRINTIFY_WEBHOOK_SECRET` for this shop and environment. Use the same secret in the Printify webhook subscription. Do not reuse this secret across shops: Printify's signed delete payload can omit `shop_id`, so the subscription's secret binds it to the configured shop.
4. Set a separate random `CRON_SECRET` of at least 32 characters. The example worker schedule runs every minute; verify current hosting-plan support, configure it explicitly and verify execution using the rollout steps below. Vercel adds `Authorization: Bearer <CRON_SECRET>` automatically; never put this credential in a URL or client environment variable.
5. Register a webhook for the exact topic `product:publish:started` using `POST /v1/shops/{shop_id}/webhooks.json`, with `url` set to the deployed `/api/webhooks/printify` endpoint and `secret` set to `PRINTIFY_WEBHOOK_SECRET`. Registration credentials need `webhooks.write`; use `webhooks.read` to inspect and read back the subscription. These management scopes are not needed just to receive events.
6. Enable `PRINTIFY_PUBLISHING_ENABLED=true` and verify the receiving endpoint and scheduled worker in that deployment. Apply and initialize [background catalog observations](catalog-background-refresh.md) as part of rollout. Coordinate registration and enablement so legitimate events are not sent to a disabled deployment. Use separate subscriptions, secrets, and database data for preview testing; a preview must not compete with production for one shop's publishing callbacks.

Keep both publishing credentials and the cron secret out of Git, terminal output, screenshots, browser bundles, and `NEXT_PUBLIC_` variables. Updating an environment value requires restarting or redeploying the application that reads it. `NEXT_PUBLIC_SITE_URL` is embedded at build time, including its use in server callbacks: build the production deployment with this store’s permanent canonical HTTPS origin (the same value as `NEXT_PUBLIC_SITE_URL`), rebuild when that value changes, and verify the reported external handle. A runtime-only override does not change an already-built canonical URL. Production setup and publication require their own authorized rollout.

The dedicated publishing token separates operation permissions, not provider accounts or shops. Follow [Printify token rotation and shared rate limits](store-setup.md#printify-and-the-first-product): personal access tokens expire after one year, and additional tokens do not add API capacity. Record expiry/rotation evidence without retaining token values.

## Per-minute recovery rollout

The example recovery cadence is **every minute**. [Example schedules](../scripts/vercel-crons.example.json) include a publishing GET trigger plus separate stock/popularity and optional order-alert jobs. The default [Vercel configuration](../vercel.json) contains no cron jobs. Review current plan support and costs, merge the needed entries, then deploy; a preview deployment does not run production schedules.

No hosting subscription is supplied by the template. Official [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing), checked **2026-09-27**, permit once-per-minute schedules on Pro/Enterprise and at most once daily on Hobby. See [how cron jobs run](https://vercel.com/docs/cron-jobs). Keep stock/popularity schedules alongside publishing recovery; an operating publishing worker does not refresh the complete catalog stock observation.

During the separately authorized rollout:

1. Configure the production credentials, fresh database, and canonical URL above. Keep publishing disabled until the complete connection is ready.
2. Perform the authorized production deployment with the root configuration and coordinated webhook/feature enablement.
3. Verify the schedule in Vercel's Cron Jobs settings, then verify a successful authenticated invocation and completion of a deliberately queued test event. Missing `CRON_SECRET` returns 503; an authenticated trigger with publishing disabled returns 200 with a disabled reason. Neither a deployed function nor a skipped invocation establishes that recovery is active. Preview environments require direct authenticated test invocations because Vercel schedules target production.

The per-minute schedule is a recovery opportunity, not a one-minute completion guarantee: provider outages, backoff, backlog, and uncertain callbacks can delay completion or require review. Vercel does not retry a failed cron invocation and can miss or duplicate invocations. The durable inbox, bounded worker, and connection/row locks retain unfinished work for later runs. Monitor job age and `attention` states as well as the function's HTTP status. See [Vercel authentication and delivery behavior](https://vercel.com/docs/cron-jobs/manage-cron-jobs).

## Maintenance commands

Use the pinned Node 24 runtime and installed `tsx` runner. The `react-server` condition permits these server-only maintenance imports; it does not expose them to browser code. The commands below do not print credentials. Choose the environment file deliberately.

```sh
node --env-file=.env.local --conditions=react-server --import tsx scripts/printify/register-publishing-webhook.ts
node --env-file=.env.local --conditions=react-server --import tsx scripts/printify/reconcile-publishing.ts
node --env-file=.env.local --conditions=react-server --import tsx scripts/printify/backfill-published-images.ts
```

Fresh stores populate the catalog through normal signed publication events from reviewed drafts.

Webhook registration uses `PRINTIFY_WEBHOOK_ADMIN_TOKEN`, with `webhooks.read` and `webhooks.write`, separately from the runtime product token. Its default lists existing subscriptions and reports the proposed canonical callback. Append `--apply` only for the intended registration. It reuses an exact existing topic/URL match, stops if another publishing subscription conflicts, and reads back after its single create attempt. The API readback does not establish secret equality, so an existing subscription's `secretVerified:false` requires a signed delivery check. Run registration once at a time; Printify does not document an atomic idempotency key for webhook creation.

Reconciliation accepts no apply option. It scans at most 20 product pages within a two-minute provider deadline and reads at most 500 open publication jobs in a read-only database transaction. It reports locked products without an open job and jobs whose product is currently unlocked or missing. Changed totals, duplicate product IDs, or exceeded limits abort the report instead of presenting partial data as complete. Provider and database reads are not one atomic snapshot; investigate a mismatch before acting on it. Reconciliation never creates a publication from an inferred missing webhook.

## Published mockup hosting

Publication copies the selected, validated mockups into a **public Vercel Blob store** before activating the replacement snapshot. The published catalog, Merchant Center feed, and product structured data then use the same hosted image URLs. Original image bytes and variant/default-image associations are preserved. Content hashes give unchanged images stable URLs and changed images new URLs; the immutable objects use a one-year cache lifetime. Hide/Show and publication with images deselected retain the existing published images without fetching saved draft mockups. A color curated in the [store-managed product gallery](product-gallery-workflow.md) keeps its approved photos regardless of what publication selects; the snapshot still holds the provider mockups.

The private snapshot retains each original mockup URL in `source_src`; catalog normalization excludes this provenance field from public product data. Reusing a receipt or hosted URL checks that its object still exists. Moving to another Blob store or repairing a missing object requires the original source bytes to match the existing content hash. A changed source produces `IMAGE_SOURCE_CHANGED` for review instead of silently replacing previously published artwork.

Vercel charges image transformations for requested cache `MISS` and `STALE` variants. The [image configuration](../next.config.ts) has 19 widths, two formats, and quality 75: requesting every combination once would require `distinct source URLs × 19 × 2` transformations. Browsers request a subset; long-lived immutable originals reduce repeat work. AVIF remains enabled because the representative 640px mockup was 27% smaller than WebP, with slower initial encoding. Review current [transformation and cache pricing](https://vercel.com/docs/image-optimization/limits-and-pricing), separate CDN/Blob costs, and [Pro's shared monthly credit](https://vercel.com/docs/plans/pro-plan#monthly-credit) before rollout; the credit is not a dedicated free transformation quota.

Before enabling this behavior in an environment, apply [the fresh database baseline](../supabase/migrations/20260928000354_storefront_baseline.sql), connect its public Blob store, and configure `NEXT_PUBLIC_PRODUCT_IMAGE_BLOB_HOST` as the exact store hostname, such as `example.public.blob.vercel-storage.com`. The hostname is intentionally public and is embedded in the image optimizer's build configuration; rebuild when it changes. Configure supported Blob SDK authentication on the server: Vercel OIDC with `BLOB_STORE_ID`, or `BLOB_READ_WRITE_TOKEN` where required. Keep storage credentials server-only and separate preview storage/data from production. Application changes do not provision the store or migrate production automatically.

Uploads have bounded download sizes and request deadlines. Image validation fully decodes at most 25 megapixels with Sharp's `failOn: "truncated"`: harmless decoder warnings are tolerated, while truncated or corrupt files are rejected without changing the original bytes. Validate every current published mockup before rollout. Completed uploads have durable receipts, so later worker invocations resume a partially copied image set. The previous published revision remains active until all replacement images are ready. Failed or interrupted work must not activate a partially hosted snapshot or acknowledge publication prematurely. Keep previous objects while any published revision or historical record can reference them; ordinary publication does not delete prior images.

An unset Blob hostname prevents publishing services from starting, leaving queued jobs pending. Runtime storage configuration errors or a changed recovery source put the job in terminal `attention` with its safe error code and do not send Printify a publication-failure callback. Fixing the environment alone does not requeue an attention job: review the stored event, published revision, and current provider state before a deliberate recovery.

The image backfill command defaults to a read-only database inventory of at most five active published products. It reports image counts and products blocked by pending or callback jobs, without contacting Printify or Blob. Terminal attention jobs do not block an images-only backfill; revision checks still protect against a newer publication. Configure `DATABASE_URL`, its TLS certificate, `PRINTIFY_SHOP_ID`, and `NEXT_PUBLIC_PRODUCT_IMAGE_BLOB_HOST` for this inventory. `--limit 1..5`, `--product-id ID`, and `--after-product-id ID` select a bounded batch; the product and cursor options are mutually exclusive.

After reviewing the inventory and authorizing the intended environment, append `--apply`. Apply uses `CRON_SECRET` and `NEXT_PUBLIC_SITE_URL` to call the deployed backfill route; it never writes to the database directly from the CLI. The route authenticates before any database/storage work, accepts at most 1 KiB of JSON, and processes at most five products and ten new image uploads per product with a 40-second work budget inside its 60-second invocation. It uses each frozen published snapshot, never current Printify drafts, and updates only images if the revision is still current and no publication job intervened. Each successful replacement creates a history revision. A batch containing any updated or already hosted product refreshes the published catalog caches once, making retry safe after a commit whose response or cache refresh was interrupted.

Use the returned `nextAfterProductId` with `--after-product-id` for the next batch when `hasMore` is true. Retry `partial` products and failures whose `disposition` is `retry` with `--product-id`. Failures marked `review` need their safe error code investigated first: `IMAGE_SOURCE_INVALID`, `IMAGE_SOURCE_CHANGED`, and `IMAGE_CONTENT_INVALID` identify source/image problems; `IMAGE_STORAGE_CONFIGURATION` and `IMAGE_STORAGE_CONFLICT` identify storage problems; `IMAGE_BACKFILL_UNKNOWN` requires reviewing the unexpected operation failure. No provider response, image URL, or credential is included in the failure report. Review `skipped` products for an active publishing job or busy worker before retrying.

The separate `cacheInvalidation` result is `not-needed`, `complete`, or `failed`. A failed refresh reports `IMAGE_CACHE_INVALIDATION_FAILED` with `disposition:retry` and leaves committed products listed as `updated`; rerun an updated or unchanged product to refresh caches without creating another image revision. The CLI exits nonzero for any product failure or failed cache refresh. It does not automatically retry an uncertain request, and HTTP 200 alone does not establish that every product finished. After the separately authorized deployment and backfill, verify public image access and refresh Merchant Center's daily catalog source so Google receives the hosted URLs.

## Event handling and publication results

The event envelope contains `id`, `type`, `created_at`, and `resource`. The event type must be `product:publish:started`, and the resource type must be `product`. Create/update actions require the configured `shop_id` and `publish_details`; the adapter retains selected flags for title, description, images, variants, tags, key features, and shipping template. A supplied shop ID must match even for delete events.

The durable event ID prevents duplicate deliveries from applying a publication twice. A session advisory lock excludes competing workers for the same product. Intake and publication decisions use short product-row transactions that recheck the latest event; provider network calls do not hold those row locks. One connection is reserved for worker activity and two for intake/read activity, so slow provider calls cannot occupy every connection needed to accept a newer signed event. An overlapping worker on the same store instance returns as busy immediately instead of waiting for that connection; jobs remain eligible for a later run. Connection failures still surface as failures. Processing and callback phases remain independent: a committed publication must not be reported as failed merely because its success callback timed out.

A current signed delete event removes the local product first, before reading Printify. A provider outage or malformed upstream product must not keep that unpublished product purchasable. Its acknowledgment is separate: a missing source product or an unlocked, invisible product can confirm completion; an unlocked, visible product requires attention while the local removal remains in place. Known later events and ambiguous equal timestamps guard stale work. A newer event that has not yet arrived cannot be ordered from local history alone, because Printify supplies no publication-generation token.

The supported **Hide on API** event sends `action:update` with every publication flag false; the locked source product's boolean `visible` carries the requested state. Visibility-only Hide/Show updates retain the last published snapshot and change only visibility. A hidden snapshot remains in history but is excluded from browsing and checkout. Show restores the same published title, prices, production details, and Primary image without importing saved drafts. These requests validate product/shop identity and explicit visibility independently of production fields and bind callbacks to the source timestamp, so an invalid design draft cannot prevent hiding its listing. Full publication, checkout, and fulfillment validate recognized production fields.

Use these Printify acknowledgments after the corresponding local result:

- `publishing_succeeded.json`: Confirm publication or a Hide/Show update, passing the stable external product ID and canonical storefront product URL. This releases Printify's publishing lock and sets its external listing reference. The durable `published` outcome denotes a synchronized non-null snapshot, including one whose visibility is false.
- `publishing_failed.json`: Report a publication that could not be applied, with a fixed, non-sensitive reason. This releases the lock while the prior published snapshot remains available.
- `unpublish.json`: Notify Printify after the product has been removed from the storefront. Retain the durable job and product history; do not delete fulfillment records or print sources.

The database keeps published products in `commerce.printify_products`, publication history in `commerce.printify_product_revisions`, and delivery/work state in `commerce.printify_publish_jobs`. Product snapshots contain private fulfillment details; expose only the existing presentation-safe catalog model to the browser.

Home, shop, and product details share a tagged published-snapshot cache with five-minute revalidation. Publication and removal invalidate it immediately; request memoization also avoids duplicate reads within one render. Availability comes from a complete background database observation, refreshed every 30 minutes in batches of 50 products. The publication transaction also saves the worker's existing live stock read with the revision; this newer stock bridges new publications and Show actions until the next scan without another provider request. It requires both `is_available` and `is_enabled`, matching production fingerprints, and stock less than two hours old. No page or feed load calls Printify, even during an outage. These checks never replace a published title, price, color membership, or Primary image with draft content. A disabled Primary color remains pictured and selected but cannot be ordered. Checkout and fulfillment perform uncached checks and remain the final ordering authority.

## Recovery and monitoring

The health endpoint also monitors the background catalog observations before browsing expires: stock warns at 65 minutes (`CATALOG_STOCK_STALE`), popularity at 13 hours (`CATALOG_POPULARITY_STALE`). Invalid payloads/fingerprint versions and unavailable observation storage have dedicated signals accepted by the existing GitHub monitor. Use authenticated catalog-sync POSTs to force a recovery scan without altering stored timestamps. See [catalog refresh operations](catalog-background-refresh.md) for all codes and the staged initialization procedure.

Inspect `state`, `outcome`, `attempts`, `next_attempt_at`, and `failure_code` on publication jobs when a product remains in Publishing. `pending` needs processing; `callback` has a persisted local result awaiting its Printify acknowledgment. `complete` is finished, `superseded` is an older event, and `attention` requires review. Transient failures before sending a callback receive bounded retries; eight unsuccessful processing attempts require attention. Check the worker trigger's execution history as well as Printify's webhook delivery results.

Monitor error-level `PRODUCT_SCHEMA_DRIFT` logs. The product parser emits this fixed code when recognized print-area or print-detail settings are malformed, including during checkout and fulfillment. These requests fail because the app cannot validate settings used in its production comparison; extra provider attributes do not cause this signal. Display stock alone is not proof of checkout compatibility. The signal excludes payloads, field names and values, and credentials. Inspect the affected required fields privately and verify the fix against checkout and publication behavior. Emitting the signal does not configure an external alert subscription.

### GitHub failure notifications

The optional `Publishing monitor` workflow is disabled until repository variable `PUBLISHING_MONITOR_ENABLED=true`. Set `PRINTIFY_MONITOR_URL` to this store's exact HTTPS `/api/internal/printify-publishing/health` URL and optionally `PRINTIFY_MONITOR_ASSIGNEE` to the responsible GitHub username. When enabled, it checks every thirty minutes and can be run manually from Actions. Its dedicated `PRINTIFY_MONITOR_SECRET` belongs in Vercel's Production environment and this repository's Actions secrets. Generate at least 32 random characters; use the same value in both locations, then deploy. It is separate from `CRON_SECRET` and the Printify tokens. GitHub receives only this health credential: database and provider credentials stay on Vercel. The monitor runs only on this repository’s default branch, with read access to code and write access to issues.

`GET /api/internal/printify-publishing/health` requires that bearer and never starts a worker or changes any data. Every response is uncached. It reads job counts, at most 500 open-job product IDs, and at most 100 active product IDs using a read-only database transaction. A strict two-page inventory scan (up to 100 products) checks identities, duplicates, and totals, and flags source locks without a received open job, including unpublished drafts. It also fetches active products directly from Printify and runs the same product parser used by checkout. Inventory and active-product validation run together with at most four provider requests in flight. Inventory reserves one request slot until its scan completes, then that slot returns to active-product validation. The two inventory pages share one thirty-second budget, individual product requests retain five-second timeouts, and the overall check retains its forty-second deadline. Inventory gets more time because its larger responses can take over ten seconds. Sharing the inventory budget allows a slow page to use time the other page does not need; overlapping the checks prevents inventory latency from consuming the active-product validation budget. Request timeouts report `PRINTIFY_TIMEOUT`; other provider failures report `PRINTIFY_UNAVAILABLE`, and exhausting the overall deadline reports `CHECK_INCOMPLETE`. Inventory read failures log only a fixed issue code, page number, headers/status/body phase, elapsed milliseconds, and the numeric HTTP status for rejected responses, so Vercel can distinguish provider HTTP errors from transport or body failures without logging response bodies or credentials. Overall-deadline cancellations still report `CHECK_INCOMPLETE` but do not emit a provider-error log. Partial scans, malformed or missing products, inaccessible services, missing configuration, and disabled publishing all report unhealthy. A latest publication that completed with `outcome=failed` also alerts until a newer event takes its place; a successful delete with `SOURCE_DELETED` does not. `attention` jobs alert immediately; pending/callback jobs become overdue only when more than ten minutes past `next_attempt_at`, so a provider-directed backoff is respected. The response exposes fixed issue codes and aggregate counts, never product payloads, customer information, or credentials.

After an unhealthy result, the workflow waits thirty seconds and checks again. If the second result is unhealthy, it opens one issue, assigned to the configured username when present. An existing open monitor issue suppresses repeat comments and issues. When the confirmed signal set changes, the monitor updates only that issue's signals and monitor-run link, preserving operator notes. Unchanged signals cause no body update, even when their ordering changes. The linked run is the evidence for the last signal change, not necessarily the latest check. A later healthy check comments with a recovery link and closes it. The Actions run summary records current health; a successful workflow means the check and incident handling completed, **not** necessarily that production is healthy. A workflow failure means the monitor could not run or update its incident and also needs attention. Enable notifications for assigned issues and failed Actions runs in [GitHub notification settings](https://github.com/settings/notifications). [Scheduled workflow notifications](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs) go to the workflow creator, or whoever last changes its schedule/re-enables it.

This is a periodic compatibility and job check, not a log drain, payment test, or proof of idle cron/webhook delivery. It detects continuing schema drift on active products, but a short-lived error between runs can be missed. It detects a stopped worker when jobs become overdue; it can flag a source lock with no received job, but cannot recreate a missing event or prove that an unlocked product had no missed updates. Use the strict read-only reconciliation command above to investigate source locks and inventory totals. An empty catalog may be intentional and is not itself a failure. GitHub's [scheduled runs can be delayed or dropped](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), so thirty minutes is the requested cadence rather than a delivery guarantee. The workflow does not require paid fulfillment to be enabled. For private repositories, consider scheduled Actions usage and the account's allowance; other CI shares that budget. Public/private billing and plan rules must be checked for the new account. See [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

To rotate the monitor secret, update both secret stores and redeploy; run the workflow manually after the deployment is ready. Before considering the setup complete, verify unauthorized health requests are rejected and an authenticated production check succeeds. Manually run the workflow with `test_notification=true` to create a clearly labeled issue, verify assignment to the intended account, and close it. This test option runs only after production health passes; it never fabricates a production failure. Confirm receipt in GitHub notifications. Never manufacture a failed production job or place an order to test notifications.

Printify expects HTTP 200. Its documentation says 4xx/5xx deliveries are retried up to three times, followed by a one-hour webhook block during which new requests are not sent. The documentation does not establish a delivery timeout, retry interval, ordering guarantee, or replay coverage for events missed during a block. The durable worker can recover events that were received; it cannot manufacture missing event history.

Do not reset a job or send a success/failure callback solely because a product is locked. Compare the stored event, current published snapshot, and current Printify product first. The worker records send intent durably before its callback POST. After an uncertain send, it reads back state without resending; if the product remains locked, it marks the job for attention. Generic fetch rejection, socket/reset errors, request timeout/abort, HTTP 408, and HTTP 5xx are uncertain outcomes. Explicit connection-setup failures (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `UND_ERR_CONNECT_TIMEOUT`) and HTTP 429 permit bounded retries; a valid `Retry-After` is honored up to one hour. Other HTTP 4xx responses require attention as `CALLBACK_REJECTED` so credentials or payloads can be corrected. No provider error body is persisted or logged.

Confirmation requires the expected external product ID, equivalent canonical URL, and visibility matching the saved snapshot. Callback readback checks visibility against the saved publication contract. URL comparison normalizes the host, default port, and trailing slash while preserving origin, path, query, and fragment identity. Source timestamps and content fingerprints detect changes but do not prove publication-attempt identity: Printify exposes no publication-generation key that could prove a repeat targets the same attempt. Visibility-only fingerprints use a `visibility-v1:` prefix so retries retain their original scope. Resolve ambiguous ordering and changed source content before retrying. If an event was never received, restore delivery and deliberately retry publication or perform an individually reviewed recovery.

Printify documents a global API limit of 600 requests per minute. Its separate 200-requests-per-30-minutes limit is specifically for initiating `/publish.json`, which this receiver does not call; do not assume that limit applies to the result callbacks. The worker still handles HTTP 429 explicitly.

The API examples include an integer `out_of_stock_publishing` without defining its meanings. This adapter does not invent a mapping for it. Published listing content and retail prices remain isolated from saved drafts. As a conservative ordering rule, a live variant must also remain enabled and in stock before checkout and fulfillment: disabling a variant in Printify pauses ordering immediately. Printify describes enabled variants as a publication selection but does not expressly guarantee that disabled variants remain orderable. See [variant properties](https://developers.printify.com/#variant-properties).

Production fingerprints are versioned as `v2:<sha>` and scoped to the selected variant's print area. They preserve stable artwork identity, placement, supported image/text/font/pattern settings, and production defaults; response-only image URLs, names, and transient `imageId` values do not identify a new design. Extra response attributes are stripped before validation and hashing; the comparison covers the recognized production settings listed in the parser. See [image properties](https://developers.printify.com/#image-properties).

Persisted jobs keep their original production identity. Inspect pending work before changing the fingerprint algorithm; never rewrite an identity to force an uncertain match.

## Print-area response compatibility

Validation is limited to fields the application consumes. Extra response attributes are stripped at the product, variant, option, print-area, placeholder, image, pattern, and print-detail object boundaries. This includes `country`, `canvas`, artwork-image `src`/`name`/`imageId`, and option-group names: their values or types cannot fail the check or affect v2 fingerprints. Optional mockup images are validated separately; an unusable image is skipped instead of invalidating the product.

| Validation kept                                                                                                      | Why it matters                                                                                 |
| -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Product/shop IDs and unique variant IDs                                                                              | Bind the response and order to the intended product and variant.                               |
| Product title and option IDs/titles                                                                                  | Build the checkout line item and selected variant label.                                       |
| Integer prices and enabled/available flags                                                                           | Quote usable prices and prevent ordering unavailable variants.                                 |
| Blueprint/provider, variant SKU/options, and print-area assignments                                                  | Preserve the existing versioned production identity and unambiguous variant-to-design mapping. |
| Artwork ID, geometry, layers, text/fonts, patterns, decoration, colors, and supported print defaults                 | Compare the recognized settings that determine the printed design.                             |
| Publishing configuration, database/provider access, job failures, source locks, and bounded complete inventory scans | Detect a real publishing problem or report when the monitor could not establish health.        |

Malformed recognized print settings still emit `PRODUCT_SCHEMA_DRIFT`; added response metadata does not. Fingerprints cover recognized production settings, not every future provider attribute. The production identity uses the current versioned fingerprint; unknown versions cannot prove a match.

## Validate the complete connection

Run the unit tests for the signature adapter, webhook route, worker trigger, processor, and database store, followed by the repository checks. These use fixtures or an isolated database and do not establish live Printify delivery.

The enabled HTTP/browser suite uses a production Next.js build, its real webhook and worker routes, and a separate local Postgres database. Install the [local test prerequisites](ci.md#local-test-prerequisites), create an empty disposable `store_publishing_e2e` database, then rebuild the fixture from the current source before each run:

```sh
pnpm test:e2e:prepare
PUBLISHING_E2E_DATABASE_URL=postgresql://postgres:local-commerce-test@localhost:55479/store_publishing_e2e pnpm test:e2e:publishing
```

The suite rejects remote hosts, other database names, and connection-string overrides. It replaces only this disposable database's `commerce` schema. Its loopback provider stub accepts synthetic credentials, records every callback, and blocks external fetches; it never registers a webhook or changes a Printify product. Tests cover signed create, invalid signature, duplicate delivery without an extra revision or callback, saved-draft isolation, selective images/Primary selection, published-price shipping quotes, unpublish/404/checkout rejection, and authenticated worker recovery without another webhook. Recovery advances the local retry timestamp instead of sleeping through production backoff. Desktop and 390px runs retain Primary-selection screenshots in the HTML report. The [required PR integration jobs](ci.md) create the isolated environments and run these suites, with a manual dispatch available for diagnosis; missing required configuration fails rather than becoming live-provider evidence. `pnpm check:all` includes it.

For the separate integration check, use a designated test product and verify all of the following:

- Publish creates one durable job and one storefront snapshot, and Printify exits Publishing after acknowledgment.
- A duplicate delivery leaves the same job and published revision in place.
- Saving a draft edit without publishing preserves the public snapshot. Selective publication changes only the selected fields.
- Temporarily interrupt processing after enqueue; the scheduled worker completes the existing job without requiring a new delivery.
- Interrupt acknowledgment after committing publication; recovery recognizes a confirmed provider result or requests review, without rebuilding the product or falsely failing it.
- Hide removes the product from browsing and checkout eligibility; Show restores the same published snapshot despite saved draft edits. Delete removes its snapshot while preserving history and existing orders. Verify these separately: `unpublish.json` acknowledges a delete result and does not initiate the merchant's Hide action.
- Modified signatures, wrong-shop events, invalid bearer credentials, and disabled deployments cannot write publication data.

Printify's prose documents create, update, and delete actions, while its OpenAPI schema currently omits update from the action enum. The adapter follows the prose and accepts all three. Verify real create, selective-update, and unpublish deliveries before production registration is considered complete.

References: [Printify API, webhook security, and publishing lifecycle](https://developers.printify.com/), [Printify OpenAPI specification](https://developers.printify.com/openapi.json), [Next.js after](https://nextjs.org/docs/app/api-reference/functions/after).
