# Dependency maintenance

Use the Node and pnpm versions pinned by `.node-version` and `package.json`. Keep runtime updates in Dependabot's existing PRs when available; don't race the bot with a second package upgrade. Next, `@next/*`, and `eslint-config-next` share a dedicated version-update group. Minor and major version updates are ignored for this family so supported-line patch updates remain eligible after a newer minor ships. Minor and major upgrades follow the deliberate patch-review process below. Security updates remain separate and may require a patch rebase outside the current range.

## The Next metadata patch

`package.json` uses `next@~16.4.2` to apply `patches/next@16.4.2.patch` to compatible patch releases in the 16.4 line. The patch filename records its original base; it is not the version selector. Runtime Next remains pinned to an exact version.

[pnpm 10 supports version-range patch selectors](https://pnpm.io/10.x/cli/patch#patcheddependencies). An exact `next@16.4.2` selector makes the patch unused when Next moves to a later patch version; pnpm rejects the lockfile update. The range lets a patch update proceed while retaining normal errors for unused patches and patches that no longer apply. Do not enable `allowUnusedPatches` or `ignorePatchFailures` to bypass these checks.

Run `pnpm test:dependencies` after installing dependencies. The offline regression uses the eight actual installed patch targets, reverses the patch in a disposable directory, and packages them as local Next fixtures. It proves the exact selector rejects a simulated patch upgrade, the configured range preserves all eight patched files, the next minor is rejected, and changed upstream content fails installation. It uses a private temporary pnpm store and removes its fixtures afterward. This proves pnpm behavior, not compatibility with an unreleased Next version.

For an actual upgrade, run the frozen install, baseline checks, production build, and the metadata browser journeys in `e2e/seo.spec.ts` and `e2e/canonical-navigation.spec.ts`. Patch application alone does not prove correct navigation or ISR metadata. Minor or major upgrades need deliberate patch review: remove it only after reproducing the original behavior without it and confirming the upstream fix, or regenerate it against the new base and update its supported range.

Require the metadata browser journeys for the exact Next dependency PR head before merge. The focused commerce PR suite does not cover every ISR/navigation regression. Run **Check** manually with **suite: full** on that head: `gh workflow run check.yml --ref '<dependabot-branch>' -f suite=full`, replacing the placeholder with its actual head branch. Find the resulting run with `gh run list --workflow check.yml --branch '<dependabot-branch>' --event workflow_dispatch --json databaseId,headSha,conclusion,url`, confirm its `headSha` matches `gh pr view PR_NUMBER --json headRefOid --jq .headRefOid`, and wait for that run to finish successfully with `gh run watch RUN_ID --exit-status`. Replace `PR_NUMBER` and `RUN_ID` with the actual identifiers. Repeat after the PR head changes. For an older generated store without this suite input, dispatch its full integration workflow instead and verify the same exact-head coverage. A green Foundation or commerce build alone is insufficient for this dependency-specific requirement.

When an upgrade needs a new patch, work in an isolated checkout and use the exact reviewed release in place of `<version>`:

1. Read the [Next.js security advisories](https://github.com/vercel/next.js/security/advisories) and release notes directly. Registry audit results and generated PRs are separate signals; an empty result does not certify a release. Check Dependabot's update-job errors and the actual dependency diff when an expected Next update is missing, including when another package in a grouped PR updates successfully.
2. Prepare a disposable standalone directory outside the store checkout, with a private `package.json`, the same pinned `packageManager`, and an exact `next` dependency on the reviewed version. Run `pnpm install --ignore-scripts` there, then `pnpm patch next@<version> --ignore-existing`. pnpm requires the target version to be installed before patching; the flag only skips applying an existing patch. Inspect the returned directory and reapply the intended eight-file behavior, checking how `htmlLimitedBots` reaches prerender and regeneration code and whether blocking metadata avoids an abandonable Suspense boundary. Do not simply discard hunks whose context changed.
3. Still in the disposable package, run `pnpm patch-commit <returned-directory>`; this generates the patch and runs an installation. Review the result, then copy only the generated patch into the isolated store checkout. Update its runtime pin and patch selector/path together, removing the old selector and choosing the deliberately supported patch range. Name a newly rebased patch for its new base; retain the original filename when its contents did not change. The store keeps its existing patch until the replacement is ready.
4. Run `pnpm install --lockfile-only`, then `pnpm install --frozen-lockfile` and `pnpm test:dependencies`. Review the lockfile for patch hashes and unintended package changes.
5. Run the baseline checks and the fresh production metadata journeys described in [metadata verification](metadata.md#verification-and-upkeep). Require full CI before merge. Record the tested version and patch evidence for every generated store that receives the update; changing this template does not update existing stores.

The publishing browser fixture intercepts both `fetch` and Node HTTPS: Next 16.4's image security fixes moved optimized-image downloads to the latter. Its HTTPS mock accepts only the synthetic Blob host, immutable image paths, and GET requests, forwarding them to the loopback provider after Next's DNS/SSRF checks. Keep image optimization and those production checks enabled; a fetch-only mock no longer exercises a working published image.

## Storybook with Next 16.4

Storybook's Next adapter 10.6.2 still supplies the older `parentCacheNode` router context, while Next 16.4's `useRouter` reads `parentRenderTree.data.bfcacheId`. This crashes the framework redirect boundary before any story renders. `patches/@storybook__nextjs-vite@10.6.2.patch` adds the missing render-tree data to the adapter's existing mock context and preserves its older fields. The exact version selector deliberately requires review when upgrading the adapter.

Run the complete `pnpm test:stories` interaction and accessibility suite after a change to either package. Remove this patch when an upstream adapter provides the new context and the same stories pass without it; do not skip failing stories or patch the production router to accommodate a test adapter.

## Stripe SDK 23

Stripe 23 uses API version `2026-09-30.endive`; the checkout client explicitly pins that version. The [Endive migration](https://docs.stripe.com/changelog/endive/2026-09-30/remove-payment-method-types-checkout-sessions) removes the `payment_method_types` request parameter. This store already uses dynamic payment methods and does not send that parameter. Keep that behavior when editing Checkout Session creation.

The webhook handler verifies signatures with the SDK's default timestamp tolerance and retrieves the session before fulfillment; it does not depend on the webhook's embedded session fields beyond its ID. The checkout and signed-webhook regressions cover these contracts, including expired signatures. Repository tests use offline providers and do not establish live Stripe acceptance or change an account's default API or webhook endpoint version.

## Repository security settings

Dependabot version updates in `.github/dependabot.yml`, vulnerability alerts, and automatic security updates are separate controls. For each newly generated repository, an administrator should enable and verify Dependabot alerts and automatic security updates; template files do not prove these settings carried over. Review an unresolved Next alert and its update-job error even when another dependency PR is green. The Next version-update group does not configure security-update grouping; verify any repository-specific grouped-security-update setting separately. Check secret scanning and push protection separately according to the destination account's available features and policy. Do not change organization defaults as part of one store's setup.
